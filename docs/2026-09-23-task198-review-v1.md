## Review

**Verdict: rework.** The structure is right: the server now owns the run task, and each session has an attachment with a replay watermark. But there are two blockers and several concurrency holes, and the two `task181_reconnect` tests never exercise the detached code path. I did not rerun the tests; everything below comes from reading the code.

### Blockers

1. **Reattaching replays permission prompts, and answering one kills the run.** `load_session.rs:306-320` pushes every buffered message through `handle_message_content`, including `ToolConfirmation` and `Elicitation`. The plan says these must not be replayed as ordinary events (bullet 3).
   - Scenario: A allows a tool, A drops, B loads. B gets a stale permission prompt and answers it. `submit_tool_confirmation` returns "already answered" or "different decision" (`agent.rs:1536-1547`). The callback then calls `cancel_token.cancel()` (`server.rs:1883`) and the run dies.
   - It is worse when a prompt was pending at the moment A dropped. The failed request maps to `Permission::Cancel` (`server.rs:1866`), which becomes DenyOnce (`agent.rs:1531`). So a lost socket is a reject today, and B is then asked again about a request that was already denied.
   - Replay also restarts tool-title enrichment, which makes a provider call for every replayed tool request.
2. **After a reload, the in-flight turn has no user prompt.** `history_boundary` is read before `reply()` saves the prompt (`server.rs:2672`). The normal prompt path saves it and never sends it as an event (`agent.rs:2288-2291`). B's replay is `history[..boundary]` plus the buffered turn, so B sees a reply with no question above it. The code comment at `:2672` says the opposite, and no test checks for a user message chunk.

### Should-fix

3. **The run pauses while no client is attached, and cancels after 10 minutes.** Every branch of `forward_agent_stream` (`server.rs:2474-2596`) waits for a connection before it reads the next event. So the provider stream stops being read while detached.
   - Real provider streams will time out long before 10 minutes, and at 10 minutes `:976-978` cancels the run anyway.
   - This goes against plan bullet 2 (only completion, cancel, shutdown or producer failure ends a run) and against the card ("keeps coming").
   - Along with the single `connection: Option<RunConnection>` slot, this is the main thing that makes 199 harder: multi-subscriber support needs an event log decoupled from the producer, not a patch.
4. **Any error is treated as a disconnect.** The retry loops (`server.rs:2491`, `:2530`, `:2578`) and `send_final_usage_to_attachment` (`:2290`) react to *any* `Err` by dropping the current connection. That includes an elicitation schema error or a failed session read. The client is still connected and will never reload, so the turn hangs for 10 minutes and is then cancelled. Before this commit, those errors ended the prompt with an error.
5. **Finishing a run can wait up to 10 minutes on a client.**
   - The success path sends the "no active run" update and final usage (both of which wait for a connection) before `clear_active_run` (`:2773`).
   - If the run completes while no client is attached, the session stays locked and the agent stays pinned for up to 10 minutes. Then the run is cancelled and reported as an error, even though the turn was saved.
   - It should clear the run first; a later load then takes the normal path and replays the saved history.
6. **Two races leave the client's "run active" indicator wrong.**
   - (a) "No active run" is sent before the run is cleared (`:2756` vs `:2773`). A client that sends its next prompt quickly gets "session already has active run".
   - (b) `:2784` checks whether *any* run exists on the session, not this `run_id`. If the next prompt has already started, the old task sends "no active run" and hides the new run's Stop button.
   - (c) If the run completes between `load_session.rs:262` and the state lock at `:287`, the run-id check still passes. B then gets `Some(run_id)` and never a matching `None` whenever the final `None` was "delivered" to A's dead but undetected socket. The attachment has no outcome field to check.
7. **A resumed turn can leak its run.** In the resume path (`load_session.rs:408`), `?` runs after `start_active_run` and before any drop guard exists. A session read error leaves the run registered and the agent pinned for good, and every later prompt on that session is refused.
8. **Locks are held across network sends.**
   - `attach_active_run` holds the attachment's state lock from `load_session.rs:287` through every replay send, so the producer waits on B's replay.
   - `finish_run_attachment` (`server.rs:936`) holds the global registry lock while waiting for that state lock, so one slow replay stalls run start and finish on every other session.
   - The plan's §Risks says no lock is held across a network send.
9. **The tests don't prove the claim.**
   - AFTER is released only after B has attached (`acp_server_test.rs:473`). So no send to A's dead connection ever happens, and `wait_for_run_connection` and its `Notify` wakeup are never run. Output produced while detached, completion while detached, and the watermark race are all untested.
   - The session is brand new, so `history_boundary` is 0 and the slicing is trivially correct.
   - There is no check that B sees the user prompt, and "one turn persisted" counts only assistant messages, so a duplicated user prompt would pass.
   - `Arc::ptr_eq` holds anyway through the shared `AgentManager` from task 197; it doesn't show that the attach path ran.
   - Wanted: a variant that releases AFTER before B connects, a session with prior history, and a user-chunk assertion.

### Nits and things that make 199 harder

- On a run-id mismatch, `attach_active_run` has already registered the session and removed its closed-id entry (`load_session.rs:282-290`), then falls through to `prepare_session_for_activation` on a live run. The same thing happens in the gap in `on_prompt` between `start_active_run` and `begin_run_attachment`.
- `closed_session_ids` belongs to each connection (`server.rs:1152`), but the task calls `clear_active_run` on A's server object. A close from B never reaches it.
- `RunConnection.server` keeps A's whole server object alive until a send to it fails.
- A second load quietly takes the only connection slot, and the first client stops receiving updates with no error.
- Tool notifications and usage updates aren't buffered, so they are lost across a reconnect.
- The turn buffer grows without bound, one entry per streamed chunk.
- A cancel while detached returns an internal error rather than `StopReason::Cancelled`, and the reply stream is dropped mid-turn.

### What checks out

- **Parity:** both agent loops are exercised, because the `unrolledAgentLoop` meta key matches `use_state_machine_from_meta` (`server.rs:467`). The resumed state-machine turn path has no reconnect test.
- **Cancel:** `session/cancel` still works on a server-owned run: `on_cancel` uses the shared `active_runs` registry.
- **Close:** `on_close_session` cancels the token, which ends a detached wait.
- **Desktop reload:** the desktop loads with `mcpServers: []`, so the attach path's refusal when MCP servers are passed won't block it.
